---

Every review runs the scanners you enable for the repository against the checked-out head commit. They are all open source, pinned by version and SHA-256 checksum, and baked into the sandbox image. Each runs as its own step, so one failing does not stop the others.

| Scanner | Finds | Runs on a pull request when it changes |
|---------|-------|----------------------------------------|
| [OpenGrep](#opengrep) | Injection, XSS, SSRF, path traversal, unsafe deserialization and other code flaws | Always |
| [OSV-Scanner](#osv-scanner) | Known-vulnerable and known-malicious dependencies | A lockfile |
| [Gitleaks](#gitleaks) | Hard-coded API keys, tokens and private keys, in every commit of the pull request | Always |
| [Trivy](#trivy) | Misconfigured Dockerfiles, Kubernetes, Helm, Terraform, CloudFormation and Azure ARM | A Dockerfile, Terraform, YAML or JSON file |
| [zizmor](#zizmor) | Exploitable GitHub Actions workflows | `.github/workflows/`, `.github/actions/`, `action.yml` or `dependabot.yml` |

A scanner whose files a pull request didn't touch is skipped, and the run page says so. Branch reviews run every enabled scanner. You choose scanners per repository under **Scanners** in the repository's **Review policy**. See [Repository settings](/docs/repository-settings).

## Why these scanners

The scanners are the cheap, deterministic first pass. The [AI review](/docs/ai-review) then triages what they found and reads the diff for what rules can't express, such as broken access control and business-logic flaws. So the aim is high-signal findings across the common vulnerability classes, not the longest possible list.

Each was picked over its alternatives for a reason:

- **OpenGrep**, not Semgrep CE: it is the community fork of the same engine, with cross-function taint analysis that Semgrep keeps for its paid tier. Semgrep's registry rules can't be used here because of their license. CodeQL's license doesn't allow it on private repositories without GitHub Advanced Security.
- **OSV-Scanner**, not Trivy, for dependencies: OSV.dev merges GitHub's advisories with each ecosystem's own database (PyPA, RustSec, the Go vulnerability database and others), and is the only open database of malicious packages, from the OpenSSF. OWASP Dependency-Check matches on CPE names from the NVD, which produces many false positives.
- **Gitleaks**: the most widely used open-source secret scanner, with about 200 rules for specific providers.
- **Trivy**, for infrastructure-as-code only: its checks cover the most formats and run offline.
- **zizmor**: workflows run with the repository's secrets, and attacks on them, such as `pull_request_target` checkouts and `${{ }}` script injection, are among the most exploited on GitHub. zizmor is the dedicated open-source auditor for them.

## Hardened against the pull request

The scanners read files written by the pull request's author. So none of them honours anything the pull request could use to switch it off:

| Scanner | Ignored |
|---------|---------|
| OpenGrep | `nosemgrep` / `nosem` / `noopengrep` comments, `.semgrepignore` |
| OSV-Scanner | `osv-scanner.toml` (an empty config is passed instead) |
| Gitleaks | `.gitleaks.toml`, `.gitleaksignore`, `gitleaks:allow` comments |
| Trivy | `trivy.yaml`, `.trivyignore` |
| zizmor | `zizmor.yml`, `# zizmor: ignore` comments |

None of the scanners runs the repository's code or build scripts. OSV-Scanner's call analysis, which would, is turned off.

The only network access any scanner has is OSV-Scanner's queries to `api.osv.dev`: `POST /v1/querybatch` and `/v1/query` with package names, versions and ecosystems, then `GET /v1/vulns/<id>` for the advisories. No source code leaves the sandbox. Everything else is refused. See [Security model](/docs/security-model).

## OpenGrep

OpenGrep is a Semgrep-compatible static analyzer. It follows untrusted input from where it enters a function (a request parameter, say) to where it is used dangerously (a SQL query), which is what separates a real injection from a call that merely looks risky.

```bash
opengrep scan --config /opt/opengrep-rules --taint-intrafile \
  --disable-nosem --x-ignore-semgrepignore-files \
  --exclude node_modules --exclude vendor --exclude test ... \
  --json --output /workspace/out/opengrep.json \
  --disable-version-check --quiet \
  --timeout 30 --max-target-bytes 1000000 \
  /workspace/repo
```

### Rules

About 850 rules, chosen when the image is built (`engine/container/rules/curate.py`) from four open-source packs pinned to a commit:

| Pack | Rules kept | License |
|------|-----------:|---------|
| [opengrep-rules](https://github.com/opengrep/opengrep-rules) | ~405 | LGPL-2.1 with the Commons Clause |
| [GitLab sast-rules](https://gitlab.com/gitlab-org/security-products/sast-rules) | ~390 | MIT; `rules/lgpl` LGPL-3.0 |
| [Trail of Bits](https://github.com/trailofbits/semgrep-rules) | ~32 | AGPL-3.0 |
| [0xdea](https://github.com/0xdea/semgrep-rules) (C and C++ memory safety) | ~24 | MIT |

From each pack, the curation keeps rules that find vulnerabilities and drops:

- rules outside the `security` category, rules tagged `audit` but not `vuln` (they flag a risky-looking API, not a bug), and `LOW` confidence rules;
- Terraform, Dockerfile, Kubernetes and other YAML/JSON rules, which Trivy and zizmor cover;
- hard-coded credential rules, which Gitleaks covers with fewer misses;
- rule families that match a function call without any untrusted input reaching it, such as Bandit's `assert` and `subprocess` checks, Flawfinder's checks of every `strcpy`, and `detect-non-literal-*`.

Weak-crypto and weak-randomness rules (CWE-327, 328, 330, 331, 338, 916) are kept at `info` severity: rarely exploitable on their own, but worth knowing. A rule OpenGrep can't parse is dropped at build time, since one bad rule would abort a whole scan. The build log prints what was kept and dropped from each pack.

Files under `node_modules`, `vendor`, `third_party`, `dist`, `build`, test directories and test files (`*.test.*`, `*.spec.*`, `*_test.go`, `test_*.py`) are not scanned.

### Severity and grouping

| OpenGrep severity | OpenVScan severity |
|-------------------|--------------------|
| `ERROR` with `HIGH` impact and `HIGH` likelihood | critical |
| `ERROR` | high |
| `WARNING` | medium |
| `INFO` | low |

Several rules often fire on the same line, for example a taint rule and a pattern rule for the same SQL injection. OpenVScan groups results by file, line and vulnerability class (SQL injection, XSS, command injection, code injection, SSRF, path traversal, or otherwise the CWE or rule id), keeps the most severe and lists the other rule ids with it. Rule ids have the form `<pack>.<path>.<rule>`.

OpenGrep spends at most 30 seconds running a rule on a single file, and skips files larger than 1,000,000 bytes.

## OSV-Scanner

OSV-Scanner reads lockfiles and checks every package version against [OSV.dev](https://osv.dev).

```bash
osv-scanner scan source --recursive --no-resolve --no-call-analysis=all \
  --allow-no-lockfiles --config /opt/openvscan/osv-scanner.toml \
  --format json --output-file /workspace/out/osv.json /workspace/repo
```

It supports `package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `deno.lock`, pinned `requirements.txt`, `poetry.lock`, `Pipfile.lock`, `pdm.lock`, `uv.lock`, `go.mod`, `Cargo.lock`, `Gemfile.lock`, `composer.lock`, `pom.xml`, `gradle.lockfile`, NuGet's `packages.lock.json`, `mix.lock`, `pubspec.lock`, `renv.lock`, `Package.resolved` and `conan.lock`. `--no-resolve` keeps it to the versions written in those files, so it doesn't call deps.dev to resolve manifests.

OSV groups the ids of one issue (a GitHub advisory, its CVE and the ecosystem's own id), and OpenVScan reports one finding per group, against the lockfile. The rule id is the `GHSA-` id when there is one. The title has the form `package@version: summary`, and the remediation names the lowest fixed version above the installed one, for example "Upgrade lodash to 4.17.21 or later." Severity comes from the highest CVSS score in the group: 9.0 and up is critical, 7.0 high, 4.0 medium, anything lower low.

### Malicious packages

A package version in the OpenSSF malicious packages dataset (ids starting `MAL-`) is reported as `Malicious package: name@version`, at critical severity, with instructions to remove it and treat machines that installed it as compromised. The AI can't dismiss it, the same as a secret: see [How the gate works](/docs/results-on-github).

## Gitleaks

Gitleaks finds hard-coded secrets such as API keys, tokens and private keys. On a pull request it runs twice:

- over the lines each of the pull request's commits added (`gitleaks git`), so a key added in one commit and deleted in the next is still caught. Deleting it doesn't help: it stays in the branch's history on GitHub, and anyone who can read the repository can fetch it;
- over the files at the head commit (`gitleaks dir`), which also reports secrets that predate the pull request.

```bash
gitleaks git /workspace/repo --log-opts="<head> --not <base commits>" ...
gitleaks dir /workspace/repo --config /opt/gitleaks.toml \
  --gitleaks-ignore-path /opt/openvscan --ignore-gitleaks-allow \
  --report-format json --redact --no-banner --exit-code 0 --log-level warn
```

To get that history, checkout fetches the pull request's commits, stopping at the base branch, instead of only the head commit. If that fails, for example because the base branch was deleted, it falls back to the head commit and Gitleaks scans the files only. Branch reviews and Daytona checkouts (a tarball, with no git history) scan the files only.

A secret still in the head commit is reported on its file and line, and is in the diff when that line is. A secret a later commit removed is reported on its file with no line, notes the commit that added it, and always counts as part of the change. Only the commit id is kept; Gitleaks' author name, email and commit message are dropped.

Both runs use the default rules of the pinned release. A `.gitleaks.toml`, `.gitleaksignore` or `gitleaks:allow` comment in the pull request has no effect. `--redact` keeps the secret value out of Gitleaks' output, so OpenVScan never sees or stores it. Every leak is reported as `high` severity with CWE-798, and the remediation tells you to revoke and rotate the credential, remove it from the code, and load it from a secret manager or environment variable. The AI can't dismiss a secret.

## Trivy

Trivy checks infrastructure-as-code: Dockerfiles, Kubernetes manifests, Helm charts, Terraform, CloudFormation and Azure ARM templates.

```bash
trivy fs --scanners misconfig --format json --output /workspace/out/trivy.json \
  --skip-check-update --config "" --ignorefile "" \
  --no-progress --quiet --exit-code 0 /workspace/repo
```

It uses the checks bundled in the pinned binary, needs no database and no network, and reports only failed checks, with the line range Trivy points to. Trivy's own severity is used as is.

## zizmor

zizmor audits GitHub Actions workflows and composite actions, offline, with its `regular` persona (the one tuned for few false positives).

```bash
zizmor --offline --no-config --no-ignores --persona regular \
  --format json-v1 --no-exit-codes .
```

It finds template injection (`${{ github.event.pull_request.title }}` in a `run:` script), dangerous triggers such as `pull_request_target` with a checkout of the pull request, credentials persisted by `actions/checkout`, excessive `GITHUB_TOKEN` permissions, actions not pinned to a commit, and more. zizmor's severity is used as is, except that a low-confidence finding is capped at `low`.

## Normalized findings

Each scanner's JSON output is parsed into the same shape:

| Field | Meaning |
|-------|---------|
| Source | `opengrep`, `osv`, `gitleaks`, `trivy`, `zizmor`, or `ai` for findings from the AI review |
| Rule id | The scanner's rule or advisory id, such as `GHSA-35jh-r3h4-6jhm` |
| Title and description | What was found |
| Severity | `critical`, `high`, `medium`, `low` or `info` |
| File and lines | Path relative to the repository root, with start and end lines when known |
| CWE | Normalized to the form `CWE-79` when the scanner provides one |
| Remediation | How to fix it, when known |

The raw JSON from each scanner is kept as an artifact of the review.

Each finding also gets a fingerprint built from the scanner, the rule or CWE, and the file path, without line numbers. The fingerprint stays the same when code moves, so a later review of the same pull request can tell which findings it has already commented on.

## Finding cap

Each scanner can record at most 500 findings per review. If a scanner reports more, OpenVScan keeps the 500 most severe.

## In the diff

For pull request reviews, each finding is marked as in the diff or not. This decides whether it can fail the check and whether it gets an inline comment.

- A finding with a line number is in the diff when its line range overlaps a line the pull request added or modified.
- A dependency finding is in the diff when the package and its installed version appear on a line the pull request added to the lockfile. A vulnerability in a dependency the pull request didn't change is pre-existing.
- A finding with no line number is in the diff when the pull request changed its file at all. The same applies to any file GitHub shows without a patch, such as binary or very large files.
- Findings in files the pull request deleted are never in the diff.

Findings outside the diff are still reported in the summary comment as pre-existing, but they never fail the check.

Branch reviews have no diff. Every finding counts toward the conclusion.

## Adding a scanner

Each scanner is one file in `engine/src/scanners/` with its command line, the exit codes that mean success, whether it needs network, and a parser for its JSON. To add one, also add its id to `SCANNERS` and its description and triggers to `SCANNER_INFO` in `packages/core/src/enums.ts`, install it in `engine/container/Dockerfile` with a checksum, and, if it needs the network, add a narrow rule to `scanAllowed` in `engine/src/egress-rules.ts`.
